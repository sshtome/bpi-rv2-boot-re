# BPI-RV2 (SiFlower SF21H8898): Технический справочник по восстановлению и модификации цепочки загрузки

> **Ревизия:** 2026-09-19 · **Статус:** рабочий документ проекта
> **Область:** реверс-инжиниринг проприетарного First Boot Loader (FBL), порт загрузки на NOR, bare-metal патчинг (RISC-V, ядра XuanTie C908)
> **Стиль изложения:** безличный; все утверждения разделены на «установлено» (подтверждено аппаратным логом) и «предполагается» (гипотеза).

## 1. Аппаратное обеспечение

### 1.1 Плата и SoC

| Компонент | Характеристика |
|---|---|
| Плата | Banana Pi BPI-RV2, ревизия V11 |
| SoC | SiFlower SF21H8898 (кремний семейства SF21A6826) |
| CPU | T-Head XuanTie C908 ×4, до 1.25 ГГц, RV64IMAFDC (векторное расширение опционально), 9-стадийный in-order dual-issue, L1 I/D 32К+32К, L2 256К |
| SDRAM | DDR3 512 МБ @ 1066 МГц (по схеме: «DDR3 512MB», DDRC с линиями CLK/D0~D3; лог FBL: «Detected DRAM size: 4096 Mb») |
| Источники | схема `BPI-RV2-V11-SCH-20241121.pdf` / `schematic.txt`; SDK zero_stage_boot (riscv_encoding.h, feature.c); OpenWrt BSP `BPI-RV2-SF21H8898-OPENWRT-24.10-BSP` |

Адресная карта из DTS (target/linux/siflower/dts):

| Регион | Адрес | Примечание |
|---|---|---|
| memory | 0x20000000–0x3FFFFFFF | номинально 512 МБ; фактическая доступность зависит от состояния DDR-контроллера (см. §3.5) |
| sram (iram) | 0x1c000000 | R-область (SRAM 64К+; фактически до 128–192К по пробам) |
| usb | 0x10000000–0x10080000 | в DTS — USB-регистры; на этапе boot область ремапится в скрытую X-SRAM (там исполняется код) |
| PCIe0 / PCIe1 | 0xa0100000 / 0xd0100000 | окна конфигурации |
| topcrm (CRU) | — | клоки CLK_IROM/CLK_IRAM/CLK_UART |

### 1.2 Флеш-память (SPI0)

| Устройство | Обозначение | Объём | JEDEC | Программатор |
|---|---|---|---|---|
| NOR (загрузочная) | U24, Eon EN25QH128 | 16 МБ | 0x1C | CH341A |
| NAND | U14, Winbond W25N01GVZEIG | 128 МБ | 0xEF/0xAA | SNANDer / flashrom (штатный CH341A не поддерживает) |

Распайка 8-pin обеих микросхем одинакова. Сигналы: SPI0_CLK=GPIO4, SPI0_CSN=GPIO5, SPI0_HOLD=GPIO6, SPI0_TXD=GPIO2, SPI0_RXD=GPIO3 (по схеме).

**Особенность NAND:** FBL в NAND (смещение 0x0–0x20000) хранится с soft-ECC в OOB-области. Запись этой зоны программатором не воспроизводит OOB-разметку и приводит к необратимому повреждению загрузчика. Восстановление UBI-области (0x20000+) выполняется data-only с on-die ECC и пропуском bad-блоков.

### 1.3 Режимы загрузки

Переключатель **J5** на плате: горизонтальное положение — загрузка с NAND (заводское), вертикальное — загрузка с NOR. BootROM выбирает активный CS шины SPI0 по этому джамперу (CS0=GPIO5 → NOR, CS1=GPIO36 → NAND).

### 1.4 JTAG (мультиплексирование с UART0)

По схеме платы сигналы JTAG совмещены с UART0 и GPIO:

| Сигнал JTAG | Вывод SoC | Совмещён с |
|---|---|---|
| JTAG_TDO | G22 | GPIO8 / UART0_TX |
| JTAG_TDI | F23 | GPIO9 / UART0_RX |
| JTAG_TMS | F22 | GPIO10 / UART0_CTS |
| JTAG_TCK | G23 | GPIO11 / UART0_RTS |
| JTAG_RST | E22 | GPIO12 |

Для активации JTAG-функций необходимо установить 0-омные резисторы в посадочные места **R95, R96, R97, R106** (в заводской поставке — «NC/0R DNI», не установлены).

В рамках проекта JTAG/GDB **не применялся**: вся отладка велась методом «printf-driven debugging» через UART (§4.4).

### 1.5 Отладочная консоль

UART1 (PL011, базовый адрес 0x0c301000), 115200 8N1, уровни 3.3 В TTL.

| Регистр | Смещение | Использование |
|---|---|---|
| DR | 0x00 | данные |
| FR | 0x18 | флаги; бит 0x80 = TXFE (FIFO пуст — разрешение записи) |

Установлено: штатный вывод FBL использует поллинг бита 0x80 регистра FR; использование бита 0x20 (TXFF) приводит к записи в заполненный FIFO и потере байтов (исправлено в инструментарии проекта).

## 2. Архитектура и цепочка загрузки

### 2.1 Этапы загрузки

```
BootROM (IROM, в маске)
   └─> Vendor FBL («SiFlower SF21H8898 Bootloader», проприетарный ddr_init)
         └─> zero_stage_boot (XuanTie, из SDK)
               └─> OpenSBI
                     └─> U-Boot (FIT-образ u-boot.itb)
                           └─> Linux (OpenWrt, target siflower/sf21, ядро 6.12)
```

Согласно документации XuanTie: «Before zero_stage_boot, SoC vendors must prepare ddr_init» — FBL выполняет роль vendor-стадии. Исходные тексты DDR-инициализации в публичном доступе отсутствуют.

Штатный лог NAND-загрузки (полный, получен с рабочей конфигурации):

```
SPI-NAND got mfr_id: ef, dev_id: aa
DDR init for 4096 Mb RAM...
Now DDR3 frequency is: 1066MHz!!!
waiting training!
End of... (×9)
Training has run successfully.
Detected DRAM size: 4096 Mb
ddr w1b test ok! addr:0x20000000 value:0x5a
read value is 0x5a
... (r1b, w2b/r2b @0x30300000, w4b/r4b @0x40540000, w8b/r8b @0x66099000)
<баннер FBL>
UBI → OpenSBI → U-Boot
```

### 2.2 Раскладка флеш-памяти

| Носитель | Смещение | Содержимое |
|---|---|---|
| NOR (16 МБ) | 0x00000 | кастомный FBL (custom_fbl, 0x203E8 б, далее 0xFF) |
| NOR | 0x40000 | u-boot.itb (568 670 б = 0x8AD5E) |
| NOR | 0xA0000 | FIRMWARE (sysupgrade) |
| NAND (128 МБ) | 0x00000–0x20000 | FBL (с soft-ECC в OOB; перезаписывать запрещено) |
| NAND | 0x20000–0x8000000 | FIRMWARE (UBI: u-boot.itb + OpenWrt FIT) |

### 2.3 Особенности IROM (BootROM) при загрузке с NOR

Установлено экспериментально (версии v54–v59 проекта):

1. **Сдвиг 0x70.** IROM загружает образ так, что заголовок файла (байты [0x00:0x6F]) **не попадает** в SRAM: память[0x1c005000] = файл[0x70]. Проверено прямым чтением памяти (память[0x1c005013] = файл[0x83]).
2. **Размер загружаемого блока.** Поле 0x00 заголовка FBL (значение 0x8DA0) задаёт размер кода, который IROM копирует в SRAM (36 256 байт; полный файл FBL — 128 КБ = 0x20000, кастомный — 0x203E8). Изменение поля 0x00 недопустимо: образ с изменённым полем отвергается IROM.
3. **База исполнения.** Код исполняется в X-only окне 0x10000000+ (первый вызов printf зафиксирован с адреса возврата 0x1000002F). Запись/чтение данных по адресам 0x1c000000+ попадают в ту же SRAM (R-алиас): запись по 0x1c005000+X эквивалентна записи по 0x10000000+X. Чтение X-окна как данных вешает шину.
4. **Загрузка зоны данных.** Область файла [0x8DA0:0x20000] (таблицы DDR, буферы) IROM **не** загружает; в проекте она дочитывается собственным кодом (ddr_load2) до начала DDR-тренировки.

### 2.4 Контрольная сумма FBL (проверка IROM)

```
add_checksum = ( sum8( файл[0x0000 : 0x8DA0] ) + 0x15 ) mod 256
условие приёма:  add_checksum == файл[0x08]  (заводское значение 0x42)
=>  sum8[0:0x8DA0] должно быть равно 0x2D
```

Подгонка суммы выполняется одним байтом в rodata по смещению 0x7D28. Лог IROM при неверной сумме: `BL checksum:66 add_checksum:N bldev is 0!` (bldev 0 = NOR).

### 2.5 FIT-образ u-boot.itb

Load-адрес ноды u-boot в FIT — **0x20000000** (поле @0x124, big-endian u32). Парсер FBL записывает u-boot по этому адресу. Конфигурация FIT: «Configuration to load OpenSBI before U-Boot». В окружении U-Boot рабочая переменная loadaddr = 0x22000000.

## 3. Реверс-инжиниринг First Boot Loader (FBL)

Инструментальная база: полный дизассемблер `fbl_full_vma.dis` (база VMA 0x1c005000), псевдокод `fbl_decompiled.c`, дизассемблирование ведётся по формуле трансляции §4.3.

### 3.1 Топология памяти: X- и R-окна

| Окно | Адрес | Свойства |
|---|---|---|
| X (исполнение) | 0x10000000+ | только выборка инструкций; чтение данных вешает шину; адреса возврата (ra) из вызовов принадлежат этому окну |
| R (данные) | 0x1c000000+ | чтение/запись; патчи и чтение памяти выполняются через него |

Установлено: R-окно — алиас той же SRAM, что и X-окно (запись по 0x1c005000+X == запись по 0x10000000+X).

Передача строк в printf: DDR-функция передаёт **R-адреса** строк rodata (например, a0=0x1c00c8E0 для строки «Now DDR3 frequency is: %dMHz!!!», файл[0x78E0]). Ранние наблюдения «X-адресов строк» (a0=0x10000033) были артефактом ошибки в отладочном hex-принтере.

### 3.2 Драйвер EXSPI (0x0C200000)

| Регистр | Смещение | Значение / назначение |
|---|---|---|
| CR0 | 0x000 | 0x000 |
| CR1 | 0x004 | SSE = бит 1 |
| DR | 0x008 | данные |
| SR | 0x00C | TFE=0, TNF=1, RNE=2, RFF=3, BSY=4 |
| CPSR | 0x010 | — |
| CMD0 | 0x02C | 0x8007 |
| CMD1 | 0x030 | — |
| CMD2 | 0x034 | 0x15 |

Прямая запись регистров EXSPI не даёт данных (проверено v19–v21). Рабочий протокол — вызов «живого» диспетчера FBL **0x1c005DD4** (кластер be6, файл[0xBE6:0xDC1] — не затирать).

**Структура дескриптора** (7 dword; размещается по адресу 0x1c00D600 — перемещён с 0x1c00E000 из-за пересечения с буфером зоны):

| Смещение | Поле | Значение для чтения |
|---|---|---|
| +0  | команда | 0x03 (READ) |
| +8  | адрес на NOR | байтовый адрес |
| +16 | — | 0 |
| +24 | — | 0 |
| +32 | длина | ≤256 байт на чанк |
| +40 | буфер приёма | адрес в SRAM |
| +48 | — | 0 (**обязательно**; без обнуления вызов виснет) |

Вызов: `a0 = дескриптор + 104`, `a1 = дескриптор`, `jal ra, 0x1c005DD4`.

Правила эксплуатации:
- Таблица команд диспетчера (0x1c00D860): [26]=0x03, [28]=0x00 (подменяется перед каждым вызовом; в файле — нули, заполняется рантаймом).
- После каждого вызова сбрасывать CR1 (запись 0 в 0x0C200004).
- Длина чанка ≤ 256 байт.
- Диспетчер портит t-регистры: состояние цикла чтения хранить только в callee-saved s-регистрах; `ra` сохранять в стеке.
- Диспетчер не пишет в DDR: приём только в SRAM; данные в DDR переносятся собственным кодом (lw/sw).

### 3.3 Контроллер DDR и PHY: тренировка и тесты

Главная функция DDR — FUN_00004AF8 (VMA 0x1c009AF8, пролог `addi sp,-112`):

1. printf(0x1c00C898, 4096) — «DDR init for 4096 Mb RAM...» (первый вызов printf; в проекте перехватывается патчем P-DDR @0x4B40).
2. Конфигурация контроллера (база 0xCE000000) и PHY (база 0xD0000000); пост-конфигурация после шага 1 (VMA 0x1c009B44): 0xCE0048C `ori 1536`, вызовы таймингов 0x1c009920/930/940/950/960/990, сброс 0xCE00500 (1/0), запуск PHY 0xD000304/0xD000030.
3. Ядро тренировки 0x1c008F5A (чтение таблицы частот 0x1c00E298; коды: 1066 МГц → 0x08550000; сравнения 469/625/937/1249/1875 МГц; PHY-регистры 0xA0000154…0xA044017C; вспомогательные: waiting-цикл 0x1c008EF4, таблица кодов «End of…» 0x1c008E7C).
4. Поллинг DDR: запись/чтение 0x20000000, 29 попыток; результат в 0x1c00E0F0; сверка `(x>>17) == s9`.
5. Цикл подбора частоты (VMA 0x1c00A218–0x1c00A312); печать «Now DDR3 frequency is: 1066MHz!!!» (строка 0x1c00C8E0, вызов @0x1c00A31E — «момент N3»).
6. Тесты записи/чтения:

| Тест | Адрес | Операция | Примечание |
|---|---|---|---|
| w1b/r1b | 0x20000000 | sb 0x5A / lbu | штатный «прогрев» DDR (a332/a33A) |
| w2b/r2b | 0x30300000 | sh 0x5AA7 / lhu | внутри DDR |
| w4b/r4b | 0x40540000 | sw 0x5AA71342 | вне DDR; на нефинализированном DDR вешает шину |
| w8b/r8b | 0x66099000 | sd | вне DDR; аналогично |

7. Эпилог 0x1c00A40A (ret с кодом частоты в a0). После возврата: `csrsi 0x7C1, 3`, баннер FBL, FUN_0000334E (основной цикл загрузки u-boot).

**Чтение u-boot штатным путём:** FUN_0000334E читает образ (на NAND — через UBI-вызовы FUN_0000337A) в буфер **0x21A00000**, сверяет магию **0xD00DFEED**, вызывает парсер FIT **0x1c00837A** (повторно проверяет магию: `lui a5,0x21a00; lw a4,0(a5)`; при несовпадении — обработчик ошибки 0x1c0085BC). Парсер пишет u-boot по load-адресам FIT (0x20000000).

**Влияние таймингов («прогрев» шины).** Установлено, что длительность UART-вывода между DDR-операциями существенно влияет на стабильность: строки-маркеры сокращали печать в ~4 раза, что смещало операцию sb 0x20000000 в «переходное окно» сразу после переключения частоты. С другой стороны, искусственная пауза перед первой записью также приводила к зависанию (контроллер/шина уходят в низкопотребляющий режим при отсутствии обращений). Штатная последовательность (printf → sb → puts → lbu → printf) обеспечивает требуемую фазировку.

### 3.4 CSR-регистры XuanTie C908

| CSR | Номер | Назначение | Эталонные значения (zero_stage_boot/feature.c) |
|---|---|---|---|
| MHCR | 0x7C1 | аппаратная конфигурация (биты 0–1: включение L1 I/D) | 0x11FF (без L2) / 0x10011FF (с L2) |
| MCOR | 0x7C2 | очистка L1/BTB/BHT | 0x70013 |
| MSMPR | 0x7F3 | кэш-когерентность | 1 |
| MHINT | 0x7C5 | подсказки | 0x1EE30C / 0x21AA10C (L2) |
| MHINT2/3/4 | 0x7CC–0x7CE | — | 0x180; 0x10000080 |
| pmpcfg0 / pmpaddr0-3 | 0x3A0 / 0x3B0–0x3B3 | физическая защита памяти | зафиксированы нулевыми в момент «N3» — защиты нет |

Установленные факты:
- FBL выполняет только `csrsi 0x7C1, 3` (частичное включение MHCR) после DDR-этапа; полную настройку кэшей выполняет zero_stage_boot, который в кастомной NOR-цепочке отсутствует (поток переходит сразу в парсер FIT).
- В момент «N3» (до csrsi) MHCR = 0x010011FC — L1-кэши выключены, MSMPR = 1 (когерентность уже включена FBL).
- `csrci 0x7C1, 3` (отключение MHCR) в кастомном коде приводило к потере работоспособности DDR-доступа.
- Влияние csrsi на доступ к DDR неоднозначно: в одном окружении (после csrsi) одиночные записи/чтения 0x21000000 и 0x21400000 проходили; до csrsi зафиксирован вис чтения (см. §3.5).

### 3.5 Фактическое поведение DDR-доступа после полной тренировки

Сводка измерений (версии v93–v135; «N3» — момент печати частоты, до тестов w1b–w8b и до csrsi):

| Операция / адрес | Момент | Результат |
|---|---|---|
| sb 'Z' в 0x20000000 (штатный a332) | после «N3» | **вис** (v135v1 — поток без хуков; v135v4, v135v8) |
| sb 0x5A в 0x21A00000 | «N3» | **проходит** (v135v6, маркер «p») |
| lbu из 0x21A00000 | «N3» | **вис** (v135v6: «p» без «q/r») |
| sw в 0x21A00000, пауза-печать после каждой записи | «N3» | **идёт** (v135v3: точки идут) |
| sw в 0x21A00000, пауза каждые 8 слов | «N3» | вис на 1–8-й записи (v134, v135v2/v5/v7) |
| sb побайтно, пауза каждые 64 байта | «N3» | вис до первой точки (v135v7) |
| sw+lw 0x21000000, 0x21400000 | после csrsi | проходит (v97) |
| 0x21800000, 0x21A00000 (подрядные) | после csrsi | вис (v97, v133/v134) |
| запись регистров DDRC/PHY (0xCE0048C, 0xCE00500, 0xD000304/30) | «N3» | проходит (v135v5, маркер «G») |

Выводы:
1. **Записи в DDR работают при наличии паузы между транзакциями** (одиночная запись или пауза ~87 мкс/печать после каждой); серии из 8+ записей подряд вешают шину. Предполагается недренируемый AXI-буфер записи (контроллер не финализирован: не выполнены тесты w4b/w8b, в которых, по разбору, производятся записи включения клоков и снятия ресетов мостов).
2. **Чтение из DDR вешает шину** на моменте «N3» (прямое доказательство v135v6). В окружении после csrsi чтения зафиксированы рабочими (v97) — связь требует уточнения.
3. Адрес 0x20000000 недоступен после полной тренировки даже для штатного потока (v135v1) — при том, что на NAND тот же код FBL проходит тесты w1b–w8b. Предполагается влияние различия окружения NOR-пути: заголовок FBL [0:0x70] не загружается в память (сдвиг IROM, §2.3), тогда как FBL может читать собственный заголовок в рантайме.

## 4. Методология «слепого» патчинга и отладки

Аппаратная отладка (JTAG/GDB) недоступна; единственный канал диагностики — UART1 и прошивка NOR через CH341A. Каждый цикл «гипотеза → прошивка → лог» требует ручной перепрошивки, поэтому применяется веерная генерация 6–10 версий за итерацию, каждая проверяет независимый вектор атаки.

### 4.1 Внедрение кода

| Зона файла | Размер | Назначение |
|---|---|---|
| 0x0D08–0x0DC1 | 184 б (используется 184) | nor_read: чтение NOR через диспетчер |
| 0x035C–0x038C | 48 б | ddr_load: устаревшая точка входа (мёртвое тело FUN_00000348) |
| 0x7DAC–0x8DA0 | нулевой rodata-паддинг (~4 КБ) | отладочный код (хуки, nor_load, nor_read2, ddr_load2) — грузится IROM сразу |
| 0xD9A2+ (DDR-зона) | 13 423 б | дочитывается только собственным ddr_load — код туда не размещать (printf/puts вызываются раньше) |

Размещение отладочного кода в DDR-зоне недопустимо: она загружается после первых вызовов printf/puts (подтверждено тишиной в v53).

### 4.2 ABI и правила написания hook-ов

Установленные особенности (наблюдением и дизассемблером):
- Оригинальные C-функции (printf 0x1c00AB24, puts-обёртка 0x1c00AB8A, диспетчер) портят t-регистры; диспетчер дополнительно портит часть s-регистров (зафиксирована порча s1).
- Безопасный хук обязан воспроизводить пролог вызываемой функции полностью: `addi sp,sp,-112; sd s1,24(sp)` (пропуск второй инструкции пролога printf приводил к порче s1 и невыполнению тестов w1b–w8b — корневой баг серии v105).
- Собственный код: состояние цикла только в s-регистрах; `ra` сохранять в стеке (`sd ra,40(sp)`); после диспетчера не доверять значениям регистров из стек-кадра.
- Точки выхода без возврата оформляются как `j` (например, ddr_load завершается `j 0x1c009B44` — ra затирается вложенными вызовами).
- Puts-печати могут теряться (буфер 0x1c00E340, \n→\r\n); надёжен только printf.

### 4.3 Трансляция адресов и кодирование переходов

```
Файловое смещение  = dis-адрес − 0x1C005000        (например, printf 0x1C00AB24 → файл 0x5B24)
Реальная память:   файл[X] → 0x1C004F90 + X        (dis-адрес = реальный + 0x70)
Код зоны:          файл[X≥0x8DA0] → 0x1C005000 + X (без −0x70!)
```

Кодировщик jal (`enc_j`, полный диапазон ±1 МБ) — биты из полного смещения `target − pc`:

```
instr  = ((delta >> 20) & 1) << 31
       | ((delta >>  1) & 0x3FF) << 21
       | ((delta >> 11) & 1) << 20
       | ((delta >> 12) & 0xFF) << 12
       | (rd & 0x1F) << 7
       | 0x6F
```

Абсолютные переходы в ассемблере заменяются плейсхолдерами DEAD000N (objcopy -O binary не выполняет релокацию); плейсхолдеры заполняются на этапе сборки скриптом. Байты инструкций берутся исключительно из objdump; примеры: `li a0,3` = 13 05 30 00; `lui s1,0x21400` = 37 04 14 02; `lui a4,0xA040` = 37 07 04 0A; `addi sp,-16` = 13 01 01 FF; `sd ra,8(sp)` = 23 34 11 00.

### 4.4 Диагностика зависаний

- **Глухой вис AXI.** Ошибки инициализации DDR или мостов не порождают исключений Load/Store Fault: проверка с собственным обработчиком mtvec не дала ни одного срабатывания (v115/v118). Зависание процессора — основной симптом сбоя.
- **Маркерная трассировка.** Односимвольные маркеры (A–Z, 0–9, «!»/«?»/«.») в ключевых точках; каждая версия печатает свой идентификатор («..135v3») первым выводом после загрузки зоны.
- **Тайминги как фактор.** Вызовы printf/puts создают миллисекундные задержки, работающие как «прогрев» шины; их наличие/отсутствие меняет поведение контроллера памяти (см. §3.3).
- **Контроль целостности.** После каждого патча пересчитывается чексумма IROM (§2.4); байтовые паттерны патчей сверяются с дизассемблером до сборки.
